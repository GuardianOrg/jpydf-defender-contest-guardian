## Terms used in this SOW

- **Included code changes** — all 171 exact Git diff hunks included in the
  quotation and security review. A hunk is one contiguous block in a Git diff.
- **Required context** — unchanged callers, dependencies, inherited behavior,
  routing, and external-return assumptions that must be examined to assess an
  included change. This does not request a full re-audit of unchanged files.
- **Supporting material — not a review target** — tests, build inputs,
  specifications, selected deployment files needed to compile tests, and machine
  checks supplied to understand or reproduce the candidate.
- **Guardian** — the external audit firm engaged under this SOW, not the
  protocol's `GUARDIAN_ROLE`. **Chain Defenders** — the prior external audit firm
  whose second engagement produced the remediation base.

## Required context

Unchanged code is not a changed-code target, but must be examined where it
imports, inherits, implements, calls, delegates, owns, or is called by an
included surface. This work is included in the quoted engagement effort but is
not a request to review whole unchanged files. Required context includes:

- ActivePool, CollateralRegistry, SortedTroves, JpydfToken, DToken,
  CollateralVaultLens, InterestRouter, and core consumers;
- DFUSDCPriceFeed and all current/placeholder source implementations;
- registered Strategy valuation/allocation paths and their external venues;
- Chainlink aggregators, wstETH canonical rate, shared JPY/USD provider, and
  Vault backing reads;
- PriceFeedProxy ownership/source-confirmation topology.

`DFUSDCPriceFeed.sol` is source-blob identical across the boundary, but its
metadata-free runtime changes through included `DFPriceFeedBase` inheritance.
Its inherited behavior is therefore required context even
though it is not a changed-file target.

The complete candidate source-level price/control topology and the
deployment-binding circularity trace procedure are in
[`FINAL_PRODUCTION_DEPENDENCY_GRAPH.md`](./docs/audit/FINAL_PRODUCTION_DEPENDENCY_GRAPH.md).
The source-level topology is review context. The deployment-binding procedure is
a project launch check, not deployment-script or production-deployment review under
this SOW.

This context requirement is call-chain and invariant validation, not a
whole-file re-audit of every named component or external protocol. Review the
reachable functions, state assumptions, ownership/routing, and external-return
semantics needed to decide the 171 included hunks. Unrelated functions in an
unchanged component remain outside the requested review. If an auditor concludes
that safety requires a materially broader unchanged component or new external
target, pause that review area and agree a scope/effort change before treating it as a
full additional target.

## Review objectives

The external review should answer:

1. Do normal, redemption, and urgent price paths preserve their distinct cache,
   failure, pause, and terminal-shutdown semantics for every current source?
2. Does JPY/USD handling remain safe across runtime-decimals or provenance drift,
   invalid responses, stale-but-newer rounds, repeated freeze episodes,
   same-value heartbeat updates during Forex market closure, and the exact
   30-hour normal-redemption boundary? Verify both pre-expiry re-anchoring and
   fresh-only recovery after expiry; do not treat a recent `updatedAt` as proof
   of recent market price discovery.
3. Can a source change, callback, forwarding dependency, or ownership lifecycle
   create a cycle, bypass source validation, poison a cache, or permanently DoS
   system-wide redemption?
4. Does failed-branch redemption accounting preserve denominator allocation and
   refund unused JPYdf without reallocating value to healthy branches?
5. Can deposit, redeem/redeem-with-permit, claim, or nonzero Strategy allocation
   complete unless raw underlying plus successfully read live Strategy values
   cover liabilities, and do the intended recovery functions remain usable?
6. Is reserved risk finalization authorized, atomic, invariant-checked, and
   one-shot across AddressesRegistry, BorrowerOperations, and TroveManager
   without partial synchronization, and does DFStabilityPool reject deposits
   before finalization?
7. Is `MIN_DEBT = 100_000e18` applied consistently across open/adjust entire
   debt including fees, repayment clamp, normal-redemption zombification, and
   zombie reactivation while preserving intentionally distinct close and urgent
   residual behavior?
8. Can Lido referral or native-ETH Zapper changes affect custody destination,
   collateral/debt accounting, receiver, minimum output, refund, or atomicity?

## Commercial scope decision

The 25-path, 171-hunk boundary shown in Guardian's scope interface is the current
quotation and review baseline. A later reduction is effective only after both
parties accept a revised written SOW that identifies the exact excluded hunks
and topics, recalculates size, confirms sufficient source and dependency
context, records the project's acceptance of the resulting risk, and limits
report conclusions to the retained scope. Until then, all 171 hunks remain
included. No engagement under this SOW supports a claim that the whole inherited
protocol is safe.

## Requested audit schedule

Because this is security-dense cross-contract DeFi logic, effort must be based
on the 171 included hunks, 535 final-side changed code nSLOC, and required
call-chain review—not the 6,656 whole-file context figure alone.

Guardian to begin as soon as scope is accepted. To preserve implementation time
after findings, the preferred target is **18 September 2026** for completion of

reduce review depth or change any scope boundary. If the date is not defensible,
